# Secrets Hub

Secrets Hub — собственное хранилище паролей и секретов домашней инфраструктуры. Приложение устанавливается на Debian через Docker Compose: React/TypeScript в браузере, FastAPI, PostgreSQL и nginx. Внешние сервисы, аналитика и облачная регистрация не нужны.

Хранилище поддерживает Login, API Key, Token, SSH Key, WireGuard, Environment, Certificate, Secure Note и File. Есть коллекции, теги, поиск по метаданным, роли и права доступа, история версий, временные ссылки, TOTP, генераторы, аудит, зашифрованные резервные копии и восстановление. Файлы ограничены 2 MiB каждый. Secrets Hub хранит WireGuard-конфигурации; приложение не изменяет VPN-сервер.

## Установка на Debian

Требования: Debian 12/13, Docker Engine с Compose v2, `bash`, `openssl`, около 2 GiB RAM, свободное место под PostgreSQL и копии. Используйте [официальную инструкцию Docker для Debian](https://docs.docker.com/engine/install/debian/). После установки проверьте:

```bash
docker version
docker compose version
sudo apt install git openssl
```

Скачайте публичный репозиторий и запустите установщик:

```bash
git clone https://github.com/EchoOfHONK/secrets-hub.git
cd secrets-hub
./install.sh
```

Если получили архив, распакуйте его и запустите `./install.sh` из каталога с `docker-compose.yml`.

Если ваш пользователь не имеет доступа к Docker, запускайте `sudo ./install.sh`. Членство в группе `docker` предоставляет фактически административный доступ к серверу; выбирайте способ доступа осознанно.

Установщик спросит порт, домен/IP, каталог данных, наличие HTTPS reverse proxy и желание сразу создать администратора в браузере. Пароль PostgreSQL генерируется случайно. Файл `.env` имеет права `600`. Данные приложения доступны контейнерному UID `10001`. При новой установке выберите отдельный пустой каталог данных: installer отказывается менять непустой каталог без исходного `.env`. Стандартных учётных записей и паролей нет.

По умолчанию приложение доступно на `http://localhost:8080` только с сервера. Для подключения через SSH можно открыть туннель:

```bash
ssh -L 8080:127.0.0.1:8080 user@your-server
```

Затем откройте `http://localhost:8080` на своём компьютере. При включённом LAN-доступе используйте адрес сервера и выбранный порт. Если установлен nginx с HTTPS, открывайте указанный домен. Для ежедневной работы по LAN и интернету настройте HTTPS; Clipboard API работает только в доверенном браузером контексте, например HTTPS или localhost.

## Первый запуск

Мастер настройки объясняет работу шифрования, создаёт первого администратора, принимает отдельный master password, проверяет адрес/HTTPS, задаёт имя инстанса и выдаёт recovery key с recovery kit. Сохраните kit вне сервера и скачайте его до завершения мастера. Создавайте длинные уникальные пароли. Master password и пароль входа могут быть разными; рекомендуется именно так.

После настройки войдите, нажмите **New Secret**, выберите тип и заполните поля. Значения скрыты до нажатия **Show** или **Copy**. В интерфейсе явно подтверждается копирование. Clipboard может сохраняться в истории ОС или синхронизироваться между устройствами; автоматическая очистка не гарантируется браузером.

## nginx и HTTPS

Пример reverse proxy: `deploy/nginx.conf.example`. Установите nginx и получите доверенный TLS-сертификат для своего домена. Для LAN допустим локальный CA, сертификату которого доверяют ваши устройства. Не игнорируйте ошибки сертификата.

```bash
sudo apt install nginx
sudo cp deploy/nginx.conf.example /etc/nginx/sites-available/secrets-hub
sudo ln -s /etc/nginx/sites-available/secrets-hub /etc/nginx/sites-enabled/secrets-hub
```

В конфигурации nginx замените `vault.example.com`, пути сертификатов и порт `8080`, если выбран другой. Пример предполагает TLS-сертификат уже существует. После проверки:

```bash
sudo nginx -t
sudo systemctl reload nginx
```

В `.env` задайте `APP_URL=https://ваш-домен`, `SECURE_COOKIES=true`, `BIND_ADDRESS=127.0.0.1`, `EDGE_PROXY_IP=172.30.251.1`. В **Settings → General** установите такой же URL. Перезапустите:

```bash
docker compose up -d --force-recreate api web
```

Адрес приложения — origin без пути: схема, имя/IP и при необходимости порт. CSRF и проверка Origin привязаны к этому адресу; при переносе адрес меняется в `.env` и настройках. Нет зависимости от конкретного домена. Браузер и API используют один origin; CORS для сторонних сайтов не нужен. В примере внешний nginx передаёт тела запросов без сохранения на диск; nginx контейнера буферизует их в tmpfs128MiB до отправки API. Буферизация ответов API выключена, чтобы раскрытые секреты и файлы не попадали во временные файлы прокси. При использовании другого reverse proxy обеспечьте такую же политику для чувствительных запросов/ответов.

Compose создаёт отдельную сеть `172.30.251.0/24`. API принимает proxy headers только от фиксированного IP web-контейнера `172.30.251.3`. При установке с HTTPS web nginx доверяет внешнему nginx только через gateway `172.30.251.1`, перезаписывает headers для API и передаёт HTTPS только от этого доверенного источника. В HTTP/LAN-режиме edge trust выключен (`EDGE_PROXY_IP=127.0.0.1`), а API по-прежнему доверяет только web-контейнеру. Внешний nginx должен перезаписывать `X-Forwarded-For` и `X-Forwarded-Proto`, как в примере. Прямые LAN-клиенты не могут подставить свой audit IP через headers. Не открывайте порты API/PostgreSQL. Если подсеть конфликтует с существующей Docker-сетью, измените вместе `DOCKER_SUBNET`, `DOCKER_GATEWAY`, `API_IP`, `WEB_IP`, `DB_IP`, `EDGE_PROXY_IP` (поля есть в `.env.example`). Для внешнего прокси на другом сервере укажите его точный IP в `EDGE_PROXY_IP`, откройте bind-порт для прокси и ограничьте вход firewall этим IP. Не доверяйте `0.0.0.0/0`. Cookie Secure определяется `SECURE_COOKIES`; установите `true` для HTTPS независимо от адреса контейнерного соединения.

## Шифрование и модель доступа

Секретные поля и версии шифруются AES-256-GCM библиотекой `cryptography`, с новым случайным nonce и привязкой к ID записи. Пароли пользователей хешируются Argon2id с солью. TOTP-секреты шифруются; recovery codes хранятся в виде хешей и используются один раз. Session token хранится в БД только как хеш; cookie имеет HttpOnly и SameSite=Strict, на HTTPS — Secure. Мутации защищены CSRF и проверкой Origin. Сессии истекают на сервере, поддерживаются блокировка, повторная проверка личности и выход со всех устройств. Rate limiting хранится в PostgreSQL, поэтому смена cookie не снимает блокировку.

Это серверное хранилище: сервер расшифровывает данные после проверки доступа. Master key — случайные 32 байта в `app/keys/master.key` с правами `600`. Master password защищает дополнительную копию этого ключа в БД; recovery key защищает другую копию. Работающий сервер использует локальный ключ без запроса master password при каждом рестарте. Компрометация сервера/root с доступом одновременно к БД и ключу позволяет расшифровать секреты. Используйте отдельный защищённый сервер, шифрование диска, обновления ОС и ограниченный SSH-доступ. Потеря БД не устраняется одним recovery key.

Названия, типы, коллекции, теги, username/hostname/service и notes metadata хранятся открыто для поиска и списка без массового расшифрования. **Не помещайте пароли и ключи в метаданные или название.** Секретные заметки вводите в секретное содержимое Secure Note. Постоянного индекса расшифрованных значений нет. Dashboard и Audit Log не содержат значения секретов.

Admin управляет всеми данными и пользователями. Editor создаёт и изменяет разрешённые записи. Viewer получает разрешённое чтение. Правила коллекций и индивидуальная выдача доступа определяют доступ к записям. Разрешение Copy проверяется сервером для соответствующих действий. Пользователь, которому разрешён Show, технически может переписать или сфотографировать значение; веб-приложение не может гарантировать запрет копирования увиденного.

При раскрытии, копировании, изменении, выдаче доступа, импорте/экспорте и других важных операциях создаётся запись аудита без секретного значения. В API выключен access log; nginx не пишет URL в access log. Не включайте стороннюю аналитику, запись HTTP bodies, отладку SQL-параметров и расширения браузера, которым не доверяете.

## Временные ссылки

Выберите срок, число просмотров (1 для одноразовой ссылки), отдельный пароль и разрешение Copy. Ссылка содержит случайный token в **URL fragment** `/t#token`; значение секрета не помещается в URL, token не передаётся серверу в строке запроса. Получение происходит POST-запросом. В БД хранится хеш token. Не публикуйте саму ссылку: она предоставляет временный доступ. Передавайте пароль отдельным каналом. Ссылка становится недоступна после истечения, достижения лимита или отзыва. Истёкшие ссылки удаляются фоновым процессом примерно раз в минуту. Исчерпанные ссылки сразу запрещают повторное раскрытие; разрешённое Copy уже показанного значения отдельно фиксируется в аудите до истечения или отзыва. Аудит сохраняется.

## SSH, WireGuard, импорт и экспорт

SSH-раздел импортирует OpenSSH/PEM ключи и генерирует Ed25519. Закрытый ключ открывается только явным действием; fingerprint вычисляется библиотекой `cryptography`. WireGuard импортирует `.conf`, показывает готовый конфиг и QR по запросу, экспортирует и дублирует профиль. QR содержит закрытый ключ клиента, поэтому обращайтесь с ним как с секретом.

Импорт поддерживает JSON, CSV, `.env`, SSH и WireGuard. JSON — массив записей с `name`, `type`, `tags`, `metadata`, `data` и опциональными `expires_at`/`collection_id`; те же поля использует API. CSV принимает столбцы типа записи и её поля; перед импортом проверяйте содержимое файла. Импорт одной операции выполняется целиком либо отклоняется.

Для примера структуры JSON (значения замените своими):

```json
[
  {
    "name": "Router account",
    "type": "login",
    "tags": ["server"],
    "metadata": {"username": "alice", "hostname": "router.home"},
    "data": {"username": "alice", "password": "your-unique-password"}
  }
]
```

Полный JSON-экспорт содержит открытые секреты. Он требует повторного пароля и TOTP при включённом 2FA, предупреждает пользователя и фиксируется в аудите. CSV экспортирует только метаданные. Экспорт отдельного WireGuard-конфига также требует повторной проверки личности. Не сохраняйте plaintext export в синхронизируемую папку и удалите его после использования.

## 2FA, блокировка и потеря пароля

В **Settings → Authentication** включите TOTP: повторно подтвердите пароль, отсканируйте QR в Aegis, Google Authenticator, Authy или другом TOTP-клиенте, введите код. Recovery codes показываются один раз. Сохраните их отдельно; каждый работает один раз вместо TOTP. Синхронизируйте время сервера через NTP. Повторное использование одного TOTP в том же временном окне блокируется.

В **Settings → Session** настройте блокировку после 1/5/15/30 минут бездействия или Never. Блокировка закрывает доступ к данным до проверки пароля и, при необходимости, второго фактора. **Logout all devices** отзывает другие сессии, включая текущую.

Если забыли пароль, другой администратор может установить новый. Если это невозможно, выберите восстановление на экране входа: username, recovery key из kit, новый пароль. Recovery key является полномочием администратора восстановления: он сбрасывает пароль указанного действующего администратора, отключает его TOTP и отзывает все сессии инстанса. Храните его как ключ ко всему хранилищу. Recovery codes TOTP и recovery key инстанса — разные вещи. Если потеряны пароль, recovery key и доступ другого администратора, восстановить вход штатным способом нельзя. Если потерян локальный master key, recovery key может восстановить его из envelope в сохранившейся БД при восстановлении администратора; также можно использовать переносимую password-backup либо сохранённый ключ; не создавайте новый ключ поверх существующей БД.

## Резервные копии

В **Settings → Backups** повторно подтвердите личность и создайте ручную копию с **отдельным длинным паролем**. Скачайте `.shbak` на другое устройство. Ручной переносимый backup содержит согласованный снимок данных PostgreSQL: пользователей, зашифрованные секреты и версии, метаданные, коллекции, права, аудит, настройки и master key, упакованные в один AES-GCM envelope с ключом, полученным Argon2id из пароля. Пароль не записывается в файл. Сессии и временные rate limits не восстанавливаются. Snapshot не содержит каталог и файлы других копий; существующий локальный каталог backup и его файлы сохраняются при restore.

Командная ручная копия:

```bash
./backup.sh
```

Пароль вводится скрыто в терминале, не в аргументах процесса. Файл создаётся в `DATA_DIRECTORY/app/backups/`, путь выводится после завершения. Backup — прикладной согласованный снимок БД, не raw `pg_dump`; для восстановления не нужно вручную переносить таблицы.

В настройках можно включить ежедневные копии и retention, например 7 daily, 4 weekly, 6 monthly. Час расписания — **UTC**, сервер проверяет его раз в минуту. Хранятся последние представители календарных дневных, недельных и месячных групп; общий набор — их объединение. Автоматические копии используют локальный master key (**machine mode**): для восстановления нужен исходный `app/keys/master.key`. Эти файлы сами по себе не заменяют переносимую ручную копию. Копируйте их вместе с ключом в отдельно защищённое место. Ручные копии retention не удаляет. `.env`, nginx/TLS-конфигурация, Docker images и сами файлы других backup не входят в прикладной snapshot: храните их отдельно.

Максимальный encrypted backup — 64 MiB, распакованный snapshot — 128 MiB. Контролируйте размер БД при хранении множества файлов/версий. Проверяйте свободное место и регулярно проверяйте восстановление на отдельном сервере.

## Восстановление

Через интерфейс: **Settings → Backups → Restore**, повторная проверка личности, выбор `.shbak`, пароль копии и явное подтверждение. Восстановление заменяет данные хранилища и отзывает все сессии, временные ссылки и TOTP recovery codes из снимка. TOTP остаётся включённым с сохранённым seed: войдите с кодом приложения, затем создайте новые recovery codes в Authentication. При потере TOTP используйте recovery key администратора. После восстановления войдите учётной записью из копии.

Для восстановления на существующем или новом сервере сначала установите приложение (`./install.sh`, БД должна быть мигрирована), затем:

```bash
./restore.sh /absolute/path/secrets-hub-backup.shbak
```

Скрипт требует ввести `RESTORE`, останавливает API и передаёт пароль и зашифрованную копию в offline restore через stdin, без изменения прав исходного файла. Он запрашивает пароль и перезапускает сервисы. Переносимая копия восстанавливает свой master key, создавать пользователей в мастере на новом сервере перед таким восстановлением не обязательно. Для machine-копии заранее разместите исходный master key в `DATA_DIRECTORY/app/keys/master.key`, владельцем UID `10001`, каталог `700`, файл `600`.

Повреждённый файл или неверный пароль отклоняются до замены данных. Snapshot проверяется, включая аутентификацию зашифрованных записей. Замена ключа использует защищённый fsync journal: при перезапуске после прерванного восстановления приложение согласует файловый ключ с уже зафиксированной или отменённой транзакцией БД. Сохраняйте исходную копию до проверки результата.

## Обновление

```bash
./update.sh
```

Скрипт сначала создаёт зашифрованный переносимый backup, затем для Git checkout выполняет `git pull --ff-only`, собирает образы и запускает миграции Alembic перед API. Изменённые отслеживаемые файлы требуют ручного сохранения. Для релиза из архива сначала замените исходники новым релизом, затем запустите скрипт. Храните `.env` и данные вне архива исходников. При существенном обновлении проверьте release notes и восстановление копии. Не удаляйте каталоги данных и не выполняйте `docker compose down -v` как способ обновления.

## Где находятся данные и перенос сервера

Корень данных выбирается установщиком, по умолчанию `/var/lib/secrets-hub`:

- `postgres/` — файлы PostgreSQL;
- `app/keys/master.key` — локальный ключ шифрования;
- `app/backups/` — резервные копии;
- `.env` в каталоге проекта — конфигурация контейнеров и пароль PostgreSQL.

Для переносимой миграции создайте ручную password-backup, скопируйте её на новый сервер, установите Secrets Hub и выполните `restore.sh`. Установите новый адрес в `.env` и **Settings → General**, настройте TLS, войдите, проверьте раскрытие секретов/версий и создайте новую копию. Старый сервер отключите после проверки.

Для файлового переноса без изменения версии PostgreSQL остановите весь Compose (`docker compose stop`) и скопируйте целиком каталог данных с сохранением владельцев/прав, а также `.env`; поправьте `DATA_DIRECTORY` на новом сервере. Нельзя безопасно копировать живой каталог PostgreSQL обычным `cp`. Не переносите raw postgres files между несовместимыми major versions; используйте переносимый backup.

## Диагностика и разработка

```bash
docker compose ps
docker compose logs --tail=100 api
curl --fail http://127.0.0.1:8080/health
```

`/health` проверяет приложение, подключение PostgreSQL, возможность доступа к storage и encryption subsystem. Ответ не содержит паролей, ключей или содержимого записей. До первой настройки отсутствие master key является ожидаемым состоянием. Контейнеры имеют healthcheck. Не публикуйте health/логи с конфигурацией на сторонних сервисах.

Исходники: `backend/app/`, миграции `backend/alembic/`, тесты `backend/tests/`, интерфейс `frontend/src/`. Один API worker нужен для scheduler и cache master key. Секретные данные передаются в телах HTTPS-запросов; не включайте debug logging.

```bash
cd backend
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements-dev.txt
pytest -q
```

По умолчанию тесты используют изолированный временный SQLite. Для проверки PostgreSQL задайте `TEST_DATABASE_URL` **только с отдельной тестовой БД**: тесты удаляют все её таблицы перед каждым сценарием.

```bash
TEST_DATABASE_URL=postgresql+psycopg://test_user:test_password@localhost/secrets_hub_test pytest -q
```

Тесты проверяют auth/session/CSRF/origin/rate limit, AES-GCM и привязку записи, CRUD, права, временные ссылки, срок действия, историю, импорт WireGuard/SSH/.env/JSON/CSV, TOTP/recovery, аудит, backup/restore и retention. Frontend собирается `pnpm install --frozen-lockfile && pnpm build`. Перед использованием реальных данных пройдите сценарий: Setup → Login → Create Secret → Copy → Collection → WireGuard Import → SSH → Temporary Link → 2FA → Backup → Restore, и проверьте HTTPS и права в Security Center.
